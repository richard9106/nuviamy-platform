# Client workspace and onboarding

The directory supports practice-scoped name/email/phone search, status filters and 25 clients per page. Directory creation and profile editing use a responsive side panel with essential fields first, optional insurance/contact details and permanently visible actions. Successful panel submissions open the saved client. The standalone form remains the validation fallback and does not send email.

The Overview combines administrative notes, appointment metadata and client form assignments in a newest-first activity feed (latest 50 items), with all-time/30-day/90-day and item-type filters. Administrative notes require client edit permission, are encrypted with the existing field encryption configuration and are never included in email or the client portal. They are separate from signed clinical session notes. Creation is audited without note content. There is no note edit/delete UI. Administrative notes and form delivery status are included in practice exports.

The context rail shows published sent/overdue invoice balances after payments, separating the client and insurance shares. Draft, void and paid invoices are excluded. Contact information and appointment/consultation details are collapsible. Billing, clinical, files and forms remain permission-gated sections. No account gains clinical, billing or portal permissions from this redesign.

Share forms has three stages: select active templates, choose portal/email options, then review and explicitly confirm. Without JavaScript, selection and email options are both visible before server-side review. The reviewed request is signed, bound to the initiating staff member, client, selected templates and recipient, and expires after ten minutes. Changes to the recipient/templates require review again. One submission digest is retained to prevent repeated assignment/email on double submit; a new deliberate review can send a new notification. Existing incomplete assignments for the same template are preserved, including their question snapshots.

Portal creation is optional and explicit. It reuses the existing portal account form, creates only a client-role account with an unusable password and sends the existing setup invitation. It never attaches a pre-existing staff account, reactivates inactive portal access or resets an established password. Existing active portal users receive a generic sign-in notification. Up to 30 templates can be shared per operation. Form assignments are committed before sending; provider failures retain the assignments and display a failed status. Pending means the callback did not yet report a result. Sent means provider acceptance, not confirmed inbox delivery. A fresh reviewed request can retry after checking the portal settings.

Emails contain no client names, form names, questions, responses or clinical content. Existing invitation emails contain the normal account setup link. No custom email-body editor, SMS/voice delivery, scored measures, patient consent signature workflow or automatic billing charge is introduced.

Deployment requires migration `clients.0005_client_chart_and_form_delivery` and the ordinary CI/CD static asset build. No production data or external emails are needed for local preview.
